# Safety

This document says what Valet does to your files, why it cannot lose or overwrite them in the cases we have tested, and where it can. It is written from the code, not from the plan. Where the code does less than `docs/PLAN.md` section 2.6 says, it says so.

It is also the source for the future FAQ, so each section can be read on its own.

Written against the Rust code at commit `2f398fb` (end of Phase 2 work). The file index (`index.rs` and the storage functions it uses) is not described here. Valet is a pre-release prototype. Nobody should point it at folders they cannot afford to lose.

## 1. The invariants

The seven invariants are in `CLAUDE.md`. Invariant 8 in `docs/PLAN.md` (CPU, memory and speed budgets) is not covered here.

Summary:

| # | Invariant | Status |
|---|---|---|
| 1 | Never delete permanently | Met in code, including trash as a rule action. Windows Recycle Bin edge cases not tested; no passing Windows result for the current code. |
| 2 | Never overwrite | Met on Windows by the API used; on Linux the check is not atomic (not a product target). Restore from the Recycle Bin never replaces. |
| 3 | Journal first; each file exactly once after a crash | Met for the crash states we tested: unit tests, and a kill-and-recover test (SIGKILL, Linux, fake platform), with a trash variant. Two cases leave a file twice (never zero times). Nothing tested on Windows. |
| 4 | Undo while destinations are unchanged | Met, with listed limits. Undo of trash restores from the Recycle Bin (Windows restore unconfirmed). |
| 5 | Default exclusions | Mostly met. Sources: apply only below the folders the user chose. Destinations inside an excluded folder or under a `.valetignore` are refused, with an exemption for the path shared with the scan root. Watched folders are checked when they are saved; the scan root is not checked again at scan time. |
| 6 | Skip files being written, locked files, placeholders | Partly met. Heuristics, a lock check that can be out of date, and a locked retry only in automatic passes. |
| 7 | No network except updater, license check, opt-in crash reports | Met by absence: none of those exist and no code opens a connection. |

### Invariant 1. Never delete permanently

**How the code meets it.**

- There is no call to `remove_file`, `remove_dir` or `remove_dir_all` anywhere under `crates/` or `apps/desktop/src-tauri/src` (checked with grep, tests included). The hook `.claude/hooks/guard-edit.sh` blocks adding them to non-test Rust files.
- Valet takes a file out of its place in only these situations: a `trash` action of a rule (a file, or an empty folder); the source of a verified cross-volume move; the temporary copy `.valet-tmp-<id>` after a failed or mismatched copy; a verified copy that has to be taken back because the source could not be trashed; the copy created by a "copy" action when it is undone; leftovers handled by startup recovery. Every one of them goes through `Platform::trash`.
- On Windows `Platform::trash` is `valet_platform::trash_path` (`crates/valet-platform/src/recycle.rs`), which calls the `trash` crate (version pinned to `=5.2.9`) on a short-lived thread. It first calls `can_trash` and, if that is false, returns an `Unsupported` error and leaves the file where it is.
- `can_trash` on Windows (`crates/valet-platform/src/fs_win.rs`) is true only if the drive type is "fixed", the policy `NoRecycleFiles` is not set (current user and local machine), and the per-volume `NukeOnDelete` setting is not set. Any lookup failure gives false. Network shares and removable drives are therefore refused.
- Trash as a rule action (`executor::execute_trash`, `precheck_trash` in `crates/valet-core/src/executor.rs`). Before anything is trashed the executor checks, in this order: the path is valid Unicode; the entry is not a cloud placeholder (before anything touches it); it exists; it is a regular file, or for a folder operation a directory (the planner gives folders size 0), and not a reparse point; for a file, its size and modification time equal the plan (for a folder, the modification time); a folder is empty; a file is not locked; `can_trash` is true. Only then it hashes a file (blake3, journaled as `hash_before`; a folder gets the mark `empty-folder`), journals `in_progress`, and calls `Platform::trash`. A folder is checked for emptiness again right before that call. After the call the source must be gone, else the operation fails with `VerifyFailed`. A failed precheck marks the operation `failed` without `in_progress` and without a hash.
- The only files Valet overwrites are its own: `config.json`, `app_settings.json` and `approvals.json` (`apps/desktop/src-tauri/src/commands/settings.rs`, written with `std::fs::write`), and the SQLite database.

**Tests.**

- `executor::tests::cross_volume_move_copies_verifies_and_trashes_source`: the source ends up in the (fake) Recycle Bin, not gone.
- `executor::tests::failed_source_trash_removes_the_copy_again`, `executor::tests::copy_with_hash_mismatch_trashes_temp_and_fails`: the copy is trashed, not deleted.
- `executor::tests::cross_volume_without_recycle_bin_touches_nothing`: no Recycle Bin, nothing is done.
- `executor::tests::undo_restores_byte_identical_tree`: undoing a copy sends the copy to the bin.
- `executor::tests_trash::trash_file_goes_to_the_bin_and_is_journaled`, `trash_empty_folder_records_the_empty_mark`, `trash_folder_that_is_no_longer_empty_fails_untouched`, `folder_filled_right_before_trash_fails_after_in_progress`, `trash_prechecks_fail_without_touching` (missing, placeholder, changed, locked: each fails with the right code, stays in place and is never hashed), `trash_without_recycle_bin_fails_untouched` (file and folder), `refused_trash_fails_and_keeps_the_file`.
- Planner side: `planner::tests::trash_rule_plans_trash_op_without_destination`, `trash_rule_still_applies_every_skip`, `trash_and_transfer_rules_conflict_in_rule_order`, `empty_folder_rule_trashes_empty_directories_only`, `empty_root_and_directory_chosen_as_root_are_never_candidates`, `excluded_and_hidden_empty_directories_are_skipped_not_trashed`, `recently_changed_empty_directory_is_being_written`, `empty_folder_with_age_uses_directory_mtime`.
- `recycle::tests::trash_file_leaves_dir` and `trash_missing_is_not_found` (`crates/valet-platform/src/recycle.rs`). On Linux they exercise the freedesktop trash, not the Windows one.
- Windows only: `temp_volume_supports_trash` and `trash_long_path_never_loses_the_file_silently` in `crates/valet-platform/tests/windows.rs`. The second accepts either outcome (trashed, or an error with the file still there). End to end, in `windows_e2e.rs`: `trash_rule_sends_file_to_recycle_bin_and_undo_restores_it` and `empty_folder_rule_trashes_folder_and_undo_restores_it`. None of these has a passing result for the current code (see "How to read this document").
- `fault_injection.rs` (odd iterations use the copy, verify, trash path with the fake bin; iterations 2 and 3 of every 4 send the `.txt` files to the fake bin with a `trash` rule) checks after each crash that no `.valet-tmp-*` file is left outside the fake bin and that originals exist once, at the source or in the bin.

**Not covered.**

- No test sets `NoRecycleFiles` or `NukeOnDelete`, or uses a removable drive or a network share. Only the positive case (a temp folder on a fixed drive) is tested.
- The `trash` crate on Windows runs a shell file operation with `FOF_NO_UI | FOF_ALLOWUNDO | FOF_WANTNUKEWARNING` and returns an error if the shell reports an aborted operation. What Windows does when a file is larger than the Recycle Bin's size limit was not verified, and no test covers it.
- Recovery treats a `trash` operation that was in progress as done when the file is no longer at its path. It does not look in the Recycle Bin (`executor/recover.rs`, test `recover_trash_op_by_disk_state`).
- A rule with the action `trash` that was approved for automatic organizing (see section 2, "Automatic organizing") trashes new matching files without a new preview. The files are in the Recycle Bin and the batch can be undone, but nobody looked at that list first.

### Invariant 2. Never overwrite

**How the code meets it.**

- At preview time the planner picks a free name with `next_free_name` (`crates/valet-core/src/collision.rs`). It checks the disk and also the destinations it has already given to earlier files in the same plan, ignoring case. The names are `name (2).ext`, `name (3).ext`, filling gaps first. Only the last extension is kept apart (`name.tar.gz` becomes `name.tar (2).gz`). The result depends only on the destination and on what is taken.
- At execution time every move and every copy ends with `Platform::rename_no_replace`. On Windows that is `MoveFileExW(from, to, 0)`: no replace flag, no copy flag, so it fails with `AlreadyExists` when the target exists. The check and the rename are one operation in the file system. If the name was taken meanwhile, the executor picks the next free name, writes the new name into the journal first, and tries again (up to 100 times, then it fails with `Io`).
- A cross-volume copy is written to `.valet-tmp-<operation id>` in the destination folder, opened with `create_new` (fails if the file exists), and only then renamed into place with `rename_no_replace`.
- Restore from the Recycle Bin (`valet_platform::restore_from_trash`) never replaces. It checks that the original path is free, restores the item under a temporary name `.valet-restore-<pid>-<nanos>-<n>` in the original folder (the `trash` crate's own restore replaces a file that appears at the target in between), checks again, and renames it with `rename_no_replace`. If the path is taken it returns `AlreadyExists` and the item stays in the bin. If another process takes the path during the restore, the item ends up under the `.valet-restore-*` name, given in the error, next to the other file.
- Undo never replaces either: see the undo table in section 2.

**Tests.**

- `collision::tests::*` (7 tests: first free name, gaps, double extension, no extension, dot files, determinism).
- `crates/valet-core/tests/prop_collision.rs` (proptest, 256 generated cases per property): `repeated_reservations_are_distinct_and_free`, `reservations_distinct_case_insensitively`, `stable_across_runs`, `suffix_rule_and_smallest_free_number`, `no_extension_suffix_at_end`, plus the fixed `double_extension_example`.
- `crates/valet-core/tests/prop_planner.rs` (`plan_invariants`, 64 generated trees and rule lists, and `case_variants_into_one_folder`): one op per source, destinations unique ignoring case and not present on disk, destination folder equal to the expanded template, first matching rule wins, same plan on a second run.
- `crates/valet-core/tests/integration_10k.rs` (`integration_1k`, `integration_10k`): pre-existing files at destination names are byte-identical after execute, and a collision count above zero is asserted so that renamed destinations occur. Same-volume path only.
- `fault_injection.rs`: pre-existing files at planned destination names are unchanged after kill, recovery and undo.
- `planner::tests::existing_destination_file_gets_next_free_name`, `two_planned_ops_never_share_a_destination`, `reservation_is_case_insensitive`, `copy_reserves_destination_too`.
- `executor::tests::collision_at_execution_time_gets_next_free_name` (same-volume move, cross-volume move, copy).
- `fs_win::tests::rename_no_replace_refuses_existing_destination`, `rename_no_replace_refuses_existing_directory` (run on every OS), `system::tests::delegates_rename_and_trash`, and `state::tests::platform_never_replaces_existing_files` in the app crate.
- Restore: `recycle::tests::restore_onto_occupied_path_is_already_exists_and_keeps_item` (Linux freedesktop trash; failed on the Windows runner at `6cf4f19`), `executor::tests_trash::undo_trash_onto_occupied_path_asks_then_fails_with_restore_occupied`.
- Windows only: `long_path_rename_no_replace`; end to end, `same_volume_move_then_undo_restores_tree` in `windows_e2e.rs` (a taken name becomes `a (2).pdf`, the pre-existing file keeps its content) and `undo_trash_onto_occupied_path_needs_confirmation_and_keeps_bin_item`.

**Not met / partly met.**

- Off Windows, `rename_no_replace` checks that the target is absent and then calls `std::fs::rename`. Another process can create the target in between and the rename then replaces it. The code comments say this is accepted on Linux because Linux is not a product target. The tests that run on Linux therefore show that the refusal works, not that it is race-free. No test creates a file between the check and the rename.
- The limit of 100 collision retries has no test.
- If a user file already has the name `.valet-tmp-<id>` in the destination folder, the copy fails with `Io` and nothing is overwritten (code only, no test).
- A file created at the original path in the short time between the final check and the staged restore's rename leaves the restored item under the `.valet-restore-*` name. No test.

### Invariant 3. Journal before, mark after; each file exactly once after a crash

**How the code meets it.**

- Each operation gets a `planned` row in the journal immediately before it is looked at, then `in_progress` (with the source hash) before any file is touched, then `done` or `failed` after. See section 3.
- On startup the app calls `executor::recover` before it starts the watcher and the auto-apply loop (`apps/desktop/src-tauri/src/setup.rs`). It decides every unfinished operation from what is on disk, without asking the user. The decisions are in the crash table in section 2.
- The order of steps in a cross-volume move is: copy to a temp file, fsync, compare blake3 with the hash taken before, rename into place, trash the source. The source is trashed last, so at every moment before that the original is still in place.
- By the design of the single-instance plugin, only one Valet process runs at a time, so recovery does not run while another process executes a batch (not tested, see below). `tauri-plugin-single-instance` (pinned `=2.5.5`) is the first plugin in `main.rs`, before the log plugin. In Tauri 2.12.5 (read from its source) plugins are initialized in `Builder::build` and the `setup` hook, which runs recovery, is called later from `App::run`. On Windows the plugin creates a named mutex (`<app identifier>-sim`) in its setup; if the mutex already exists, the second process passes its arguments to the first one and calls `std::process::exit(0)` inside that call (`platform_impl/windows.rs` in the plugin). The first instance shows its window, unless the second launch carries `--minimized` (the callback in `main.rs`). So a second process exits before `setup` and never reaches recovery. Inside one process, `file_ops` in `state.rs` keeps manual batches, undo and automatic passes from overlapping.
- The undo of a `trash` operation is a journaled `restore` operation (op type added by migration `0004_restore_op_type.sql`, which rebuilds the `operations` table with the wider `CHECK` and keeps rows and the autoincrement counter). A `restore` that was in progress at a crash is decided from the disk by `recover` (see the crash table).

**Tests.** `executor::tests::recover_*` (listed in section 2) and in particular `recover_leaves_every_moved_file_exactly_once`, which builds five interrupted moves (planned, not started, mid-copy, placed but source not trashed, finished) and checks that each file's content exists once, no temp file is left, and no operation stays unfinished. For trash and restore: `executor::tests_trash::interrupted_trash_is_decided_by_the_disk`, `executor::tests::recover_restore_op_by_disk_state`. The process-kill test `kill_during_apply_then_recover_and_undo` in `crates/valet-core/tests/fault_injection.rs` is described next. The single-instance behavior has no test: nothing starts two processes, and what is stated above comes from the plugin source. Migration 0004 is applied by every test that opens a database (`Db::connect` runs the migrations); no test checks the copy of old rows.

**The kill test.** Each iteration builds a fixture: 40 files of 0 to 256 KiB in three folder levels, six extensions, some sharing a name, plus pre-existing files at planned destination names. It starts `valet-fault apply` (`crates/valet-core/src/bin/valet-fault.rs`, built only with `test-support`, using `FakePlatform` with a Recycle Bin folder) as a child process, waits 10 to 500 ms and kills it with `Child::kill` (SIGKILL on Linux) unless it has finished. Then it runs `valet-fault recover` as a new process and checks:

- every original file exists exactly once (at its source, at one destination, or for files a `trash` rule took, in the fake bin) with its original blake3, and the pre-existing files are unchanged;
- no `.valet-tmp-*` file is left, no operation and no batch is unfinished, the recovery batch has a summary, and recovery decided exactly as many operations as the crash left open;
- every `done` operation has its `hash_after` at its destination and its source gone (a `done` trash operation: the file is not at its path), and every `failed` operation has error text;
- then `valet-fault undo` restores the original tree byte for byte and leaves only the pre-existing files in the destination.

Even iterations use the same-volume rename path; odd ones set `VALET_FORCE_CROSS_VOLUME=1` (copy, verify, rename, trash). In iterations 2 and 3 of every 4 the `.txt` files go to the fake bin through a `trash` rule instead of being moved. Half of the runs add a 5 to 20 ms pause after each journal change, a quarter 1 to 4 ms, a quarter none, so kills also land inside file I/O and commits. Each iteration's fixture and delays come from a fixed seed (the iteration number), but the kill time is wall-clock, so two runs do not hit the same states. The default is 10 iterations (`VALET_FAULT_ITERS`); CI sets 100.

Result of one local run with 100 iterations (this session, Linux): 0 failures, 46.2 s. 72 runs were killed during the batch, 6 before the batch was created, 22 had finished. Recovery made 49 decisions: 28 `planned` to `failed` ("never started"), 12 `in_progress` to `failed` ("not at destination"), 3 `in_progress` to `done` ("verified at destination"), and 6 `in_progress` to `failed` whose explanation the test prints as empty (the test prints only the text before the first path; by the code, an explanation that starts with a path is the one for a trash operation whose file was still in place, "is still there; not sent to the Recycle Bin"; not confirmed in this run). In 2 iterations the disk was not yet in the "exactly once" state when recovery started (this counts any failed check, not only duplicates). 91 batches were then undone. In this run no kill left an `in_progress` operation with the file at both source and destination, so the branch "copy verified at destination; source sent to the Recycle Bin" and the other branches in the crash table were exercised by the unit tests only. Other runs can land elsewhere.

**Limits of the evidence.**

- The kill test drives `planner::plan`, `executor::execute`, `recover` and `undo_batch` through the `valet-fault` driver. It does not run the Tauri app, `SystemPlatform` or Windows. The "volumes" are one volume with `same_volume` forced to false, and the Recycle Bin is a folder.
- A killed process is not a power loss. The operating system still writes out what the process had written. Power loss was not tested. The code does not set SQLite's `synchronous` setting; sqlx leaves SQLite's default (FULL), so commits are flushed in WAL mode. The `.valet-tmp` file is fsynced (`sync_all`) before the compare; a plain same-volume rename is not followed by a directory flush.
- The recovery unit tests construct the journal and disk state that a crash would leave; they do not kill anything.
- The kill test runs in CI (`core (Linux)` and the Windows job, 100 iterations). It passed in the Linux job for `2f398fb` and in both jobs for `cc00f94`. The Windows step for it failed at `2f398fb`; the annotated failures are other tests of the same run, and whether the kill test itself passed there cannot be read from them. On Windows it still uses the fake platform.

**Two cases where a file can exist twice.** In both, the file is never lost; it is present at the source and at the destination, the operation is marked `failed`, and the error text names both paths.

1. A cross-volume move (or a copy that has to be taken back) where the source cannot be trashed, and then the copy cannot be trashed either. The first failure is handled (the copy goes to the Recycle Bin and the source stays: `executor::tests::failed_source_trash_removes_the_copy_again`). The second failure has no test. The same double failure is possible in undo of a cross-volume move and in recovery.
2. Recovery of a move that was in progress, finding that the destination is a cloud placeholder while the source file still exists. Recovery does not hash a placeholder, so it cannot verify the destination; it leaves both in place and marks the operation `failed`. No test (the test `recover_placeholder_destination_with_source_gone_is_done_unhashed` covers the case where the source is gone).

**Other gaps.**

- Recovery runs only at startup. If it fails (for example the journal cannot be opened for writing), `setup.rs` logs an error and starts anyway.
- The instance lock is a named mutex without a `Global\` prefix. On Windows such a name should be limited to one logon session (from the Windows naming rules, not verified here), so the same user in two sessions at once could start two instances on the same journal. Not tested.
- There is no panic hook that marks `in_progress` operations (PLAN 4.5). A panic is treated like any crash: recovery decides at the next start.
- The test pause `VALET_FAULT_SLOW_MS` is compiled only with the `test-support` feature (`executor.rs`, `fault_pause`; without the feature it is an empty function). The app depends on `valet-core` without that feature (`apps/desktop/src-tauri/Cargo.toml`) and `valet-fault` requires it. This was checked at an earlier commit (`a461d81`) by building the library without the feature and by `strings` on the app's test binary, and not repeated for `2f398fb`. The release installer was not built. There is no test for the absence: `cargo test` turns the feature on through a self dev-dependency (the code comment says so).
- A different switch is in shipped code: `valet_platform::same_volume` (`fs_win.rs`) returns "not the same volume" when the environment variable `VALET_FORCE_CROSS_VOLUME` is `1`. In that case every move takes the copy, verify, trash path, which needs a Recycle Bin on both volumes. Nothing in it skips a check. Test: `crates/valet-platform/tests/force_cross_volume.rs`.
- Manual execution runs the list the user previewed, not a new plan. The details are in the "Execute after preview" row of section 2. The plan is kept only in memory and has no expiry. The executor re-checks missing, changed, placeholder and locked files, but not exclusions, hidden state or `.valetignore`: those are decided when the preview is made. Automatic passes plan and execute in one step; see "Automatic organizing" in section 2.

### Invariant 4. Undo while destinations are unchanged

**How the code meets it.** `executor::undo_batch` (`crates/valet-core/src/executor/undo.rs`) undoes the `done` operations of one finished `apply` batch, last first, as a new `undo` batch. Before touching a moved or copied file it hashes the file at the destination and compares with the hash recorded when it was moved. If they differ, or if the original path is now taken, nothing is moved and the operation is returned as "needs confirmation". Calling again with `force` does it anyway, still without overwriting. A `trash` operation is undone by restoring the item from the Recycle Bin (`Platform::restore_from_trash`, matching the original path and a deletion time not earlier than the operation's `created_at` minus 2 seconds; the newest match is taken), journaled as a `restore` operation. The details are in the undo table in section 2.

**Tests.** `executor::tests::undo_restores_byte_identical_tree` (same-volume and cross-volume; compares the files of the tree by content before and after; a second undo finds nothing to do), `undo_with_modified_destination_needs_confirmation`, `undo_with_occupied_source_needs_confirmation`, `undo_skips_failed_ops_and_lists_them`, `undo_copy_with_original_gone_needs_confirmation`, `undo_cross_volume_without_recycle_bin_fails_untouched`, `undo_rejects_unknown_open_and_non_apply_batches`, `recover_interrupted_undo_rolls_back_original`, `journal::tests::undo_done_and_rollback_are_atomic`. For restore: `executor::tests_trash::undo_restores_trashed_files_and_folders_with_moves`, `undo_trash_onto_occupied_path_asks_then_fails_with_restore_occupied`, `undo_trash_with_changed_content_restores_and_reports_it`, `undo_trash_missing_from_the_bin_fails_and_keeps_the_op`, `executor::tests::recover_restore_op_by_disk_state`. Larger runs: `integration_10k.rs` undoes 1,000 and 10,000 same-volume moves and compares the whole tree by content hash; `fault_injection.rs` undoes the batch that a killed and recovered run left (91 of 100 iterations in the local run, with the trash variant) and requires the original tree back, byte for byte, with no failed, unconfirmed or renamed restores. Windows only: `same_volume_move_then_undo_restores_tree`, `long_paths_move_and_undo`, `trash_rule_sends_file_to_recycle_bin_and_undo_restores_it`, `empty_folder_rule_trashes_folder_and_undo_restores_it` and `undo_trash_onto_occupied_path_needs_confirmation_and_keeps_bin_item` in `windows_e2e.rs`. None has a passing result for the current code.

**Limits.**

- The comparison is a content hash, not a "modified by the user" flag. A file edited and then edited back to the same bytes counts as unchanged.
- Only files are compared in the test; folders that a batch created are left behind (see the undo table).
- Undo cannot restore a file that was moved or deleted after the batch (`SourceMissing`, reported as a failure).
- Undo of a trashed file depends on the item still being in the Recycle Bin. If the user emptied the bin, the restore fails with `SourceMissing` and the operation stays `done` (test `undo_trash_missing_from_the_bin_fails_and_keeps_the_op`).
- Restore finds the item by original path and time. Whether this works on a real Windows Recycle Bin is unconfirmed: the CI run for `6cf4f19` shows four restore tests failing with `no matching item in the bin`, and the run for `2f398fb` has no readable result for them.
- Operations that are not `done` (failed, already rolled back) are listed as skipped and not touched.
- The Tauri commands `undo_batch` and `execute_operations` (`apps/desktop/src-tauri/src/commands/operations.rs`) take the same lock as automatic passes, so a batch, an undo and an automatic pass do not run at the same time in one process.

### Invariant 5. Default exclusions

**How the code meets it.** The planner walks each scan root with `walkdir` (`follow_links(false)`) and skips, without descending: directories whose name (ASCII case-insensitive) is one of `Windows`, `Program Files`, `Program Files (x86)`, `ProgramData`, `AppData`, `$Recycle.Bin`, `System Volume Information`, `.git`, `node_modules`, `target`, `.venv`, `venv`, `__pycache__` (`DEFAULT_EXCLUDED_DIRS` in `planner.rs`); any directory that contains a file named `.valetignore`; directories and files that are hidden (a name starting with `.`, or the Windows hidden or system attribute); reparse points; cloud placeholders. Each skip is reported with a reason (section 2).

**Watched folders.** `save_config` and `complete_onboarding` validate each folder with `validate_config` (`apps/desktop/src-tauri/src/commands/settings.rs`) and refuse it with a stable code when: it is a drive or share root (`config.driveRoot`: `C:`, `C:\`, `C:/`, `\\server`, `\\server\share`, the same with `\\?\` or `\\?\UNC\`, or `/`); a component of the path equals a default-excluded name (`config.excludedFolder`); or it does not exist (`config.missing`). The check is on path text and does not touch the disk except for existence. The user profile folder itself is allowed.

**Destinations.** The planner also checks where a file would go. After it expands the destination template (`~`, `%VAR%`, a folder token, `{year}`, `{month}`, `{day}`, `{ext}`), joins a relative folder to the scan root and resolves `.` and `..` in the path text, it skips the file as `invalidDestination` (no operation is planned) when:

- a component of the folder is one of the `DEFAULT_EXCLUDED_DIRS` names (ASCII case-insensitive), looking only at the components after the part the folder shares with the scan root; or
- the folder, or any folder above it up to the file system root, contains a file named `.valetignore`. The folder itself does not have to exist yet.

"Shares with the scan root" means the leading components of the folder that equal, ignoring ASCII case, the leading components of the root the file was found under (`in_excluded_dir` in `planner.rs`). The exemption is there because a scan root can be inside an excluded name: on Windows the temp folder is under `AppData`, where the tests create their folders. The `.valetignore` lookup has no such exemption.

**Tests.** Sources: `planner::tests::each_default_excluded_dir_is_skipped_once_and_not_descended`, `excluded_names_match_ascii_case_insensitively`, `excluded_name_only_applies_to_directories`, `valetignore_excludes_its_dir_and_everything_below`, `root_containing_valetignore_is_excluded`, `dot_file_is_hidden_and_dot_dir_not_descended`, `platform_hidden_file_and_dir_are_skipped`, `include_hidden_rule_plans_hidden_files`, `include_hidden_is_decided_by_the_winning_rule`. Also `index::tests::index_skips_placeholders_and_exclusions` for the file index. Watched folders: `commands::settings::tests::drive_and_share_roots_are_detected`, `excluded_folders_match_by_component`, `validate_config_returns_code_and_path`, `save_config_writes_only_valid_config_and_returns_it`, and `commands::presets::tests::onboarding_expands_tokens_and_validates_like_save_config`. **Partly met.**

- The exclusions apply to what is found below a scan root. A scan root is the user's choice, and a root that is itself called `node_modules`, or sits inside such a folder, is scanned (`excluded_names_in_root_path_are_an_explicit_opt_in`). The app refuses such a root when it is saved (see "Watched folders"), but the planner does not repeat the check: a `config.json` edited by hand, or written by an older version, is read by `watched_folders`, which only filters out folders that do not exist.
- The watched-folder check does not look at the hidden attribute, although the text shown for `config.excludedFolder` says "or hidden". A hidden folder that is not under an excluded name is accepted. It does not resolve junctions or symlinks.
- Exclusion is by directory name at any depth below a root, not by full path. A folder called `target` or `venv` anywhere below a root is skipped. `C:\Windows` is skipped only when it is reached from a root above it. A destination is judged the same way, by names after the shared part. So with a root such as `C:\Users\me\Downloads` a destination under `C:\Users\me\AppData` is refused, but with a root inside `AppData` every destination under that `AppData` is allowed (`excluded_name_in_the_chosen_root_does_not_block_destinations_below_it` covers a sibling folder).
- The destination check works on path text. It does not resolve junctions or symlinks, so a destination folder that is a junction into an excluded folder is not detected, and it does not check whether a destination folder is hidden or a reparse point. No test.
- A `.valetignore` in a folder above the scan root also blocks destinations: the lookup goes up to the file system root and has no exemption for the root's own ancestors. The scan itself does not look above the root. Read from the code; the test puts the marker in the destination's own path only.
- Destinations are checked when the preview is made. The executor does not check exclusions again, so a `.valetignore` created after the preview does not stop a planned operation.
- The list differs from PLAN 4.3: the code adds `venv` and `__pycache__`, and lists `Program Files` and `Program Files (x86)` as exact names instead of `Program Files*`.
- `includeHidden` (a rule option, `true` or `false`, default off) makes hidden files eligible for that rule. It does not make hidden folders scanned: hidden folders are skipped before any rule is looked at (read from the code; no test uses `includeHidden` with a hidden folder).
- Empty folders that an `emptyFolder` rule would trash are kept when they are, or contain, the destination of an enabled move or copy rule, or of a move or copy planned in the same plan (`RuleDestination`; see section 2).

### Invariant 6. Skip files being written, locked files and cloud placeholders

**How the code meets it.**

- Being written: the planner skips a file (and an empty folder) whose last extension is `crdownload`, `part`, `tmp`, `download` or `partial` (any case), whose name starts with `~$`, or whose modification time is less than 10 seconds before the time of the plan (`RECENT_WRITE_WINDOW`).
- Locked: right before acting on a file, the executor asks `Platform::is_locked`. On Windows that opens the file for reading with sharing mode 0 and closes it at once, and treats errors 32 and 33 as "locked". It reads no data.
- Changed: the executor refuses a file whose size, modification time or type differs from the plan (`ChangedSincePreview`).
- Placeholders: see the cloud placeholder row in section 2. Short version: detected from file attributes without opening the file, checked before anything else touches the file, and never hashed. Duplicate rules hash only files the scan accepted, so never a placeholder.
- Retry: in automatic passes a file found locked is tried again on the next 3 passes (see section 2, "Automatic organizing"). After a pass that skipped a file as being written, an automatic pass runs again about 12 seconds later.

**Tests.** `planner::tests::each_being_written_case_is_skipped`, `recently_modified_file_is_being_written`, `cloud_placeholder_file_and_dir_are_skipped`, `placeholder_wins_over_being_written_and_hidden`; `executor::tests::changed_size_or_mtime_fails_without_touching`, `locked_source_is_skipped`, `placeholder_is_never_hashed_or_moved`, `recover_placeholder_source_is_not_trashed_or_hashed`, `recover_placeholder_destination_with_source_gone_is_done_unhashed`; `executor::tests_trash::trash_prechecks_fail_without_touching` (placeholder and locked, trash variant). - The lock check is a snapshot. A file can become locked right after the check. Then the rename or copy fails with an `Io` error and the operation is marked `failed`; for a copy the temp file goes to the Recycle Bin. No test for that race.
- The locked retry exists only in automatic passes, only in memory (it starts over at restart), and only for the next 3 passes. A manual preview and "Organize" do not retry: a locked file fails with `Locked`.
- Real OneDrive and Dropbox placeholders have not been used in any test. Detection relies on the attributes OFFLINE, RECALL_ON_OPEN and RECALL_ON_DATA_ACCESS. A directory that carries one of them is skipped with everything below it.

## 2. What happens in each case

"Preview" is `dry_run`, which calls `planner::plan` and changes nothing. "Execute" is `executor::execute`. Before acting on a file, execute checks, in this order: the paths are valid Unicode and the destination has a folder; the source is not a placeholder; the source exists; it is a regular file and not a reparse point; size and modification time equal the plan; the file is not locked. Then it hashes the source, creates the destination folder if needed, and chooses the method. A `trash` operation has its own order of checks, given under invariant 1.

Preview reasons for leaving a file alone (`SkipReason`, camelCase in the JSON): `excluded`, `hidden`, `reparsePoint`, `beingWritten`, `cloudPlaceholder`, `conflict` (a later rule that also matches), `alreadyInPlace`, `noExtension` (a `{ext}` folder and the file has no extension), `invalidDestination`, `unsupportedAction`, `unreadable`, `ruleDestination` (an empty folder kept because a rule uses it as a destination). Test: `planner::tests::skip_reason_serializes_camel_case` (checks one value).

Execution failures (`FailCode`, stored in the journal's `error` column as `Code` or `Code: detail`): `SourceMissing`, `ChangedSincePreview`, `CloudPlaceholder`, `Locked`, `NoRecycleBin`, `VerifyFailed`, `TrashFailed`, `Occupied`, `Interrupted`, `InvalidPath`, `Io`, `RestoreOccupied` (undo of a trash: the original path is taken). A failed operation does not stop the batch.

### Crash in the middle of a batch

Each operation is written to the journal as `planned` right before it is executed, so a crash leaves at most the operation being run (and possibly its trash step) unfinished. At the next start, `recover` reads every `planned` or `in_progress` row and decides it from the disk. It compares the destination with the source hash saved when the operation went `in_progress`. It writes one `recovery` batch, whose summary lists each decision, and closes the batches the crash left open ("interrupted; recovered by batch ..."). Files that recovery has to remove (a leftover temp copy, the source of a finished copy) go to the Recycle Bin as journaled `trash` operations in that batch. A second run finds nothing to do.

| Destination is a placeholder, or locked, or not a regular file | Reported as failed (`CloudPlaceholder`, `Locked`, `ChangedSincePreview`). A placeholder is not hashed. | no test |

## 3. The journal

The journal is two SQLite tables in the same file as the rules (`valet.sqlite3` in the app's config folder, `%APPDATA%\ro.valetapp.desktop` on Windows), created by `crates/valet-core/migrations/0003_journal.sql` and widened by `0004_restore_op_type.sql`. Code: `crates/valet-core/src/journal.rs`.

**Batches** (`batches`): `id` (UUID), `kind` (`apply`, `undo` or `recovery`), `created_at`, `finished_at` (empty while the batch is open), `summary`.

**Operations** (`operations`): `id` (autoincrement, never reused, so `.valet-tmp-<id>` names stay unique), `batch_id`, `seq`, `op_type` (`move`, `copy`, `trash` or `restore`), `source_path`, `dest_path`, `size`, `hash_before`, `hash_after`, `state`, `error`, `created_at`, `finished_at`, `undo_of` (the operation an undo step reverts). The database enforces the allowed values of `kind`, `op_type` and `state` with `CHECK` constraints. For a `trash` operation `dest_path` is empty and `hash_before` is the blake3 of the file, or `empty-folder` for a folder. A `restore` operation has the original path as both source and destination; the migration adds `restore` to the allowed `op_type` values by rebuilding the table (SQLite cannot change a `CHECK`), copying the rows in id order and keeping the autoincrement counter.

**States and allowed moves.** `planned`, `in_progress`, `done`, `failed`, `rolled_back`:

| From | To |
|---|---|
| `planned` | `in_progress`, `failed` |
| `in_progress` | `done`, `failed` |
| `done` | `rolled_back` |
| `failed`, `rolled_back` | none (final) |

Any other change is rejected with `InvalidTransition` and the state stays as it was. The update itself carries the allowed source states in its `WHERE` clause, so a stale caller cannot move a row that already changed. Tests: `journal::tests::state_machine_table`, `every_disallowed_transition_is_rejected_and_state_kept`, `missing_op_is_reported`, `happy_path_records_fields_per_state`.

**What is written when.**

- `planned`: source, destination, size, written right before the operation is looked at.
- `in_progress`: `hash_before` (blake3 of the source, or `empty-folder`), written before any file is changed.
- `done`: `hash_after` and `finished_at`. For a rename or a verified copy this is the same as `hash_before`. For a `trash` it is empty.
- `failed`: `error` (`Code` or `Code: detail`) and `finished_at`.
- `rolled_back`: set on the original when its undo step is `done`.
- `dest_path` is rewritten when a collision at execution time picks a new name, before the retry, so recovery looks in the right place (`journal::tests::set_dest_rejected_once_finished` covers that a finished row refuses it).

**One transaction per state change.** Each change of state is its own transaction (`Journal::transition`). A batch is never one transaction. The only transaction that touches two rows is `mark_undo_done`: it marks the undo step `done` and the original `rolled_back` together, or neither (`journal::tests::undo_done_and_rollback_are_atomic`). `set_dest` is a single statement and not a state change.

**WAL.** `Db::connect` opens SQLite in WAL mode (`crates/valet-core/src/storage.rs`). Test: `journal::tests::connect_enables_wal`. The code leaves `synchronous` at the SQLite default.

**Other points.**

- Paths are stored as text. The executor refuses paths that are not valid Unicode before they reach the journal.
- Nothing deletes journal rows. There is no retention limit, so the journal grows. The History screen lists the newest 50 batches.
- The older `operation_history` table (the statistics and "recent operations" the UI used before the journal) is separate. `clear_operation_history` clears only that table. Test: `storage::tests::clearing_history_keeps_the_journal`.
- The journal holds full paths. It stays on the local disk.
- Rules are stored in the same database (`rules` table, listed by row id; a rule edited in place keeps its row, a new rule gets a later row; read from `Db::upsert_rule` and `list_rules` and checked with the same SQL on a scratch SQLite table, no test in the repository). The files `config.json` (watched folders), `app_settings.json` and `approvals.json` are next to it.
